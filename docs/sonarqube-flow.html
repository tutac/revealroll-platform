SonarQube Wiring

SonarQube reads your code and refuses to let it become a container image if it fails the quality gate. It runs in your own cluster, next to Grafana and Loki — one more thing Argo CD deploys from Git, plus one host setting that belongs to Ansible.

What happens on a push

Where the gate sits

The gate is placed before the image build, not after. That is the whole design: code that fails cannot become an image, so it cannot become a tag bump, so it can never reach the cluster.

Inside the cluster

What SonarQube actually is

One pod running three Java processes, one database, one disk. The memory numbers below are why this file is opinionated — the chart's defaults ask for about 5 GB of heap on an 8 GB node that is already running Prometheus, Loki and your app.

The one piece that is not Kubernetes

Elasticsearch will not start unless the host kernel allows enough memory-mapped areas. The chart's answer is a privileged container that edits the node. Ours is a line in the Ansible role that already owns the operating system — so this cluster runs no privileged container at all, and the requirement is visible to anyone reading the machine's config.

Port 6443 is firewalled shut from the internet on purpose (decision 011). Every kubectl, kubeseal and helm command below fails with connection refused until that tunnel is up. Ansible does not need it — it talks over plain SSH on port 22.

1
laptop · ansible

Set the host kernel value

Do this before anything syncs. Without it, Elasticsearch fails its startup check and the pod crash-loops with a message about virtual memory that does not mention Kubernetes.

cd ansible
ansible-playbook -i inventory/staging.yml site.yml
ssh deploy@<node-ip> sysctl vm.max_map_count   # expect 524288
2
laptop · kubeseal

Seal the two credentials

Needs your SSH tunnel to the cluster open, because kubeseal fetches the controller's public key. The script prints both values once — put them in your password manager before you close the terminal.

make tunnel            # in another terminal, if it isn't up
./scripts/seal-sonarqube.sh

Writes secrets/sonarqube/sonarqube-sealed.yaml — encrypted, safe to commit.

3
laptop · git

Commit and push — that is the deploy

Argo CD syncs three Applications in wave order: secrets, then the database, then SonarQube. First boot runs a schema migration and builds search indexes, so give it five to ten minutes. One failed retry in that window is expected and already accounted for in the Application's retry policy.

git add . && git commit -m "feat(quality): self-hosted SonarQube behind the image build"
git push

Watch it: kubectl -n sonarqube get pods -w

4
browser

First login, and set the admin password

Open https://sonarqube.stg.revealroll.com and sign in with admin / admin. It forces a change immediately. Save the new password in your password manager — deliberately, nothing in the repo can recover it, because the chart's password-setting job would otherwise fail on every single sync and leave the Application permanently red.

5
browser

Generate the scanner token

Administration → Security → Users → your account → Tokens → Global Analysis Token. Copy it once.

This is a CI credential, so it goes to GitHub — not into a SealedSecret here. Cluster credentials are sealed into this repo; CI credentials live in CI. The directions are opposite on purpose.

6
tutac/revealroll

Wire the gate into the app repo

Add the token as a repository secret SONAR_TOKEN and the URL as a repository variable SONAR_HOST_URL. Then two files — the full snippets are in docs/sonarqube.md:

sonar-project.properties     # project key, sources, coverage path
.github/workflows/ci.yml     # a `sonar` job … and then the line that matters:

  docker:
    needs: [static, ui, sonar]   # was [static, ui]

Without that last change you have a report nobody is obliged to read. With it, you have a gate.

7
verify

Prove it blocks

Push a branch with a deliberate code smell — an unused variable, a hardcoded string repeated four times. Watch the sonar job fail and, more importantly, watch docker never start. Then remove it and watch a pod actually roll.

A gate you have never seen refuse anything is not yet a gate.

Know this before someone asks

Two honest limits

Community Build reads one branch

Pull-request decoration and per-branch analysis are Developer Edition features. So this gate protects main; it does not annotate individual PRs. Knowing the licensing boundary of your own tooling reads as senior. Claiming PR decoration works here reads as the opposite.

It is reachable from the internet

GitHub-hosted runners have to reach it, and allowlisting GitHub's runner IP ranges is not practical. Compensating controls: forced authentication and a strong admin password. The answer that actually removes the exposure — and the one a regulated or federal environment would require — is a self-hosted runner inside the network.
