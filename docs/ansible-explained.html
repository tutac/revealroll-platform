The punch list that builds a server

What Ansible actually did to the Contabo box — first in plain language for anyone, then in the real file names for me.

PLAY RECAP staging-1 ok changed=0 on the second run skipped failed=0
Part one · for anyone

Start with a building inspector

Imagine a house that has just been handed over by the builder, and an inspector with a written list: the front door has a deadbolt; the smoke alarm has a battery; the back gate is locked; the boiler is switched on.

The inspector walks the house with the list. For each line she checks the real house against the sentence. Deadbolt already fitted? Nothing to do. No battery in the alarm? She puts one in. At the end she reports how many lines were already fine and how many she had to fix.

Walk the same list through the same house tomorrow and she fixes nothing, because nothing has drifted. That is the entire idea behind Ansible, and it has a name: idempotent — running it twice is the same as running it once.

Ansible is the list plus the inspector. I write down how the server should be. A program on my laptop logs into the server, compares reality to the list, and changes only what doesn't match.

Nothing is installed on the server

This is the part people find surprising. There is no Ansible daemon sitting on the VPS waiting for orders. My laptop opens an ordinary SSH connection — the same one a human would use — runs commands down it, and hangs up. The server has no idea it was "managed."

Which means the list lives in Git, on my machine, in this repository. The server is downstream of it. If the server vanished tomorrow, the description of it wouldn't.

So what did I actually build?

Four passes over one machine, in a fixed order, each one assuming the previous one finished:

  • Give myself a way in that isn't root. Create a normal user called deploy, put my laptop's key on it, let it become administrator without typing a password.
  • Make the machine hard to break into. Turn off password logins and root logins over SSH. Put up a firewall that drops everything except the few ports that must be open. Install a service that bans IP addresses after repeated failed logins. Cap how much disk the logs may eat. Let security patches install themselves overnight, but nothing else.
  • Install Kubernetes. Specifically k3s — a small, single-binary Kubernetes — pinned to one exact version, with two of its bundled extras deliberately switched off because later stages install better replacements.
  • Prove all of the above, out loud. A final pass that changes nothing and instead asserts: root login is off, the firewall does default to drop, the node is Ready, the disk does have headroom. If any sentence is false, the run fails.

That last one is the difference between "I ran a script" and "I know what the machine is." Everything before it is a claim; the fourth pass is the evidence.

Part two · the real thing

Now with the file names on

Same story, told in the vocabulary I'd need in an interview or a review — the pieces of Ansible, the order they run, and the modules that do the work.

The vocabulary, from outside in

Ansible's nouns nest. Every one of them is a layer of the same object: a description of desired state, scoped a little more narrowly than the layer outside it.

inventory/staging.yml

The machines and how to reach them. Two groups: k3s_servers holds staging-1; k3s_agents is deliberately empty. Gitignored — the committed file is .example.

group_vars/all.yml

Values more than one role needs: deploy_user, ssh_port, public_tcp_ports, base_domain, k3s_tls_sans. One place to change a shared fact.

roles/*/defaults/main.yml

Each role's own knobs at the lowest precedence, so the inventory can override them. k3s_version lives here — that is why bumping Kubernetes is a one-line diff.

roles/*/templates/*.j2

Jinja2 files rendered with those variables and written to the host. The firewall ruleset, the sshd drop-in, the fail2ban jail and the k3s config are all templates, not static copies.

roles/*/handlers/main.yml

Restarts that fire only when something above them actually changed. A task notifys a handler; the handler runs once, at the end of the play.

ansible.cfg

Run settings, not host settings. pipelining and ControlPersist=60s reuse one TCP connection for the whole play — on a 130 ms link to Germany that is minutes.

The run, in order

00-bootstrap.yml is the only play that connects as root, and it is deliberately not imported by site.yml. Its only job is to create the account every later play connects as. The moment deploy can sudo, it has no reason to run again — and the hardening play is about to close root SSH behind it.

Why the empty agent play exists

20-k3s.yml already contains the play that joins worker nodes, against a group with no hosts in it. Ansible reports "no hosts matched" and moves on. It costs ten lines now; written later, under pressure, with a worker already provisioned and waiting, it gets written badly. Adding a second node is now a Terraform entry, an inventory line, and a site.yml run.

What does the actual work: modules

A task is a name plus a module call. The module is the piece that knows how to look at the machine, decide whether reality already matches, and report ok or changed. These are the ones this build leans on.

ModuleWhat it does hereWhere
ansible.builtin.apt Installs base packages, nftables, fail2ban. Always state: present, never latest — latest makes every run a surprise upgrade and destroys changed=0. common, firewall, fail2ban
ansible.builtin.template Renders a Jinja2 file with the run's variables and writes it. Carries validate: — sshd -t, nft -c, visudo -cf — so a broken config is rejected before it lands, not after the restart takes SSH away. firewall, ssh-hardening, fail2ban, node-exporter, k3s-server
ansible.builtin.copy Small static files with no variables in them: the sudoers drop-in, the two unattended-upgrades snippets. users, common
ansible.builtin.lineinfile Edits one setting inside a file Ansible doesn't own end-to-end — the journald size caps. common
ansible.builtin.file Directories, permissions, and deletions — removing the cloud-image sshd drop-ins that would otherwise win over mine. ssh-hardening, k3s-server
ansible.builtin.user Creates deploy, and the node_exporter system account with nologin and no home. users, node-exporter
ansible.posix.authorized_key Installs my workstation pubkey, read off the laptop at run time so it never enters the repo. Not exclusive — that would delete a teammate's key mid-incident. users
ansible.builtin.systemd_service Enable + start, and mask ufw so it can't fight nftables over the ruleset. every service-owning role
get_url + unarchive Fetches the k3s installer and the node_exporter tarball. Both gated on a version check, because downloading is not idempotent by itself. k3s-server, node-exporter
ansible.builtin.command The escape hatch, used only where no module exists: running the k3s installer, reading k3s --version, sshd -T, nft list ruleset. Every read-only one carries changed_when: false. k3s-server, ssh-hardening, 99-verify
slurp + delegate_to Reads the k3s node-token off the control plane while running against a worker — the file is root-only and exists on one host, not the other. 20-k3s.yml
set_fact / stat / assert Not state, but reasoning: decide whether an install is needed, and fail loudly with a message when a precondition doesn't hold. k3s-server, ssh-hardening, 99-verify
service_facts / getent Read the machine into variables so assertions can be written against it instead of against a grep. 99-verify.yml

Two collections beyond core, pinned in requirements.yml: ansible.posix for authorized_key and sysctl, and community.general for the timezone module and the k3s-era helpers.

The one concept worth keeping: changed=0

k3s installs with a single curl | sh. The reason it is a role instead is that the installer is not idempotent: it always downloads, always rewrites the systemd unit, always reports success. Run it from a shell: task and every run says "changed", forever, and you lose the only signal that tells you whether the machine drifted.

So the role decides for itself, first, and gates everything on that decision:

The same shape appears in node-exporter: read the installed version, only unarchive when it doesn't match. Any task built on command or shell has to be given this by hand — that is the tax you pay for stepping outside a module, and the reason to step outside one as rarely as possible.

Handlers: restart only when something moved

A template that rewrites /etc/rancher/k3s/config.yaml hasn't done anything until k3s reads it. But restarting k3s on every run would mean a control plane blip every single time, for nothing. So the task notifys a handler, and the handler fires only if the file genuinely changed.

Configuration as a file, not as a flag

The k3s installer accepts its flags through INSTALL_K3S_EXEC, which bakes them into the systemd unit. This build deliberately passes only server there and puts every real flag in /etc/rancher/k3s/config.yaml, rendered from config.yaml.j2:

  • node-name — so the node registers under the name the inventory uses, not the provider's hostname.
  • write-kubeconfig-mode: 0644 — so deploy can run read-only k3s kubectl get/describe/logs during triage without sudo. A single-operator trade-off.
  • disable: [traefik, servicelb] — ingress-nginx needs ports 80 and 443. Two ingress controllers racing for the same host ports is a bad evening with very misleading symptoms.
  • tls-san — the hostnames and IP baked into the API server certificate.

k3s re-reads that file on every start, so changing a flag is a template diff and a handler restart. Bake it into the unit instead and "add a hostname" becomes a reinstall.

The caveat to know before you need it

Adding a tls-san does not reissue an existing certificate — k3s only regenerates one that's missing. Delete serving-kube-apiserver.{crt,key} and restart. The x509 error you get without doing that helpfully names the SANs it does have, which is the fastest confirmation you've hit exactly this.

If someone asks me to explain it

Five sentences, in order, that cover the whole layer:

  1. Terraform owns things that have an API before a cluster exists; Ansible owns everything inside the operating system; after that, Argo CD owns everything with a Kubernetes API — and no component belongs to two of them.
  2. Ansible is agentless: my laptop is the control node, it reaches the host over plain SSH as an unprivileged deploy user, and the description of the machine lives in Git rather than on the machine.
  3. The work is organised as roles — common, users, firewall, ssh-hardening, fail2ban, node-exporter, k3s-server — composed by playbooks whose order is load-bearing: the firewall opens the SSH port before sshd is moved onto it.
  4. Idempotency is the acceptance criterion, not a nice-to-have: the k3s installer isn't idempotent, so the role version-checks first and skips it, and a second site.yml run reports changed=0.
  5. And the last playbook changes nothing at all — it asserts that root login is off, that the firewall defaults to drop and doesn't expose 6443, that the node is Ready under the expected name, and that the disk still has 20% free.
