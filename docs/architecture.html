The organising rule

Four layers, one owner each

The temptation on a single VPS is to do everything with one tool — Ansible can run helm install, Terraform has a Kubernetes provider, k3s auto-applies manifests from a directory. Each layer exists because it has a different reconciliation model: Terraform reconciles against remote state on demand, Ansible reconciles the OS on demand, Argo CD reconciles the cluster continuously. Mixing them gives a resource two owners that disagree — a fight you did not schedule, at 2 a.m., on the thing you last touched.

Why the seam is here and not somewhere else

Terraform installs only what Argo CD needs in order to run. Everything after that is a commit — which makes “what is running in staging?” a question you answer by reading a file in Git, not by interrogating a cluster that may be the thing that is on fire.

The monitoring cannot monitor itself

node-exporter runs as a systemd unit installed by Ansible rather than as the chart's DaemonSet, so host metrics — disk, memory, load — survive the cluster being the broken thing, which is exactly when you need them. By the same logic the outermost uptime check has to live off this VPS entirely: a monitoring stack running on the machine it monitors cannot tell you the machine is down.

Why not just run helm upgrade from CI?

Security. The push model needs a kubeconfig stored in GitHub — a credential that can do anything in the cluster, sitting in a system that any workflow file, any compromised action and any contributor with write access can reach. That is exactly the class of secret the Codecov and tj-actions supply-chain incidents exfiltrated. Here, no credential that can modify the cluster ever leaves the cluster.

Auditability. git log charts/revealroll/values-staging.yaml is a complete deployment history with authors and timestamps, git blame says who shipped what, and rollback is git revert of the bump commit — an operation you already know how to perform under stress. With helm upgrade that history lives in release secrets inside the cluster.

And never :latest. A moving tag means two pods created a minute apart can run different code, describe cannot tell you what is deployed, and “roll back” has no target. sha-<commit> makes deployment identity and source identity the same string.

Triage order — most outages are answered by step 2

1. Argo CD — is the Application Synced and Healthy? Out-of-sync means Git and the cluster disagree.   2. Pods — get pods -A | grep -v Running, then read Events, not the status. ImagePullBackOff, CrashLoopBackOff and Pending have nothing in common.   3. Ingress and certs — a Pending challenge is nearly always DNS or a blocked port 80.   4. Logs — Loki, or logs --previous for a pod that already restarted.   5. Metrics — saturation or an error spike?   6. Host — df -h, free -m, journalctl -u k3s. On a single node a full disk presents as ten unrelated Kubernetes symptoms at once.

Walking someone through it

The spoken version

Sixty seconds the shape

“It's the staging environment for my own application, on one VPS running k3s, and the thing I care about in it is that every component has exactly one owner. Terraform owns anything with a provider API. Ansible owns the operating system. Terraform installs the four things Argo CD needs to exist — ingress, certificates, sealed-secrets and Argo CD itself — and then stops touching the cluster forever. Everything after that is a commit. CI builds an image and writes a one-line tag bump into the platform repo; Argo CD pulls it. No credential that can change the cluster is ever stored in CI, and rollback is a git revert.”

Three minutes add the operations

Add: the four layers with their handover artifacts; hostPort ingress because there is no cloud load balancer; secrets sealed into a public repo with the controller key backed up out of band.

Then the part that matters most — thirteen alerts, each with a runbook written before the alert; a written incident log with detection time and root cause; node-exporter deliberately outside the cluster so host metrics survive the cluster; and an uptime check off the box entirely, because a monitor that dies with its subject tells you nothing.

Five questions to be able to answer cold

  1. Walk me through your infrastructure end to end.
  2. Something broke in production — how do you triage it?
  3. How do you handle secrets in a GitOps repo, and why that choice over Vault?
  4. What would differ if you rebuilt this on AWS? (EKS for the control plane, IRSA instead of node credentials, ALB instead of hostPort, S3 + DynamoDB instead of R2 for state.)
  5. How would you add a security gate to a pipeline, and where in the stages does it belong?
